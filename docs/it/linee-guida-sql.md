### 2. Convenzioni di Naming

Uniformità e chiarezza nel codice DDL:

| Oggetto           | Convenzione                        | Esempio                               |
| ----------------- | ---------------------------------- | ------------------------------------- |
| **Schema**        | minuscolo, plurale                 | `anagrafiche`, `config`, `dbops`      |
| **Tabella**       | nome plurale, snake_case           | `soggetti`, `gestori_utilities_ruoli` |
| **Colonna PK**    | `id`                               | `id UUID`, `id SERIAL`                |
| **Sequenza**      | `<table>_id_seq`                   | `storico.comuni_id_seq`               |
| **Indice**        | `ix_<table>_<column>`              | `ix_contatti_soggetto`                |
| **Vista**         | prefisso `vw_`                     | `vw_clienti_attivi`                   |
| **Funzione**      | prefisso `fn_`                     | `fn_calcolo_fattura()`                |
| **Trigger Func.** | prefisso `trgfn_`                  | `trgfn_contatti_set_default()`        |
| **Trigger**       | prefisso `trg_`, `<table>_<event>` | `trg_contatti_insert_update`          |
| **Constraint PK** | `pk_<table>`                       | `pk_soggetti_ruoli`                   |
| **Constraint FK** | `fk_<base_table>_<ref_table>`      | `fk_contatti_soggetti`                |
| **Constraint UQ** | `uq_<table>_<columns>`             | `uq_contatti_default`                 |

💡 **Nota**  
Quando una colonna ha un significato comune e ricorrente (ad esempio `descrizione`, `nome`, `codice`), **non deve essere nominata con il suffisso del nome tabella** (`descrizione_cliente`, `nome_articolo`, ecc.), ma mantenere solo il nome semplice.  

👉 Questo garantisce coerenza nello schema e semplifica query, join e documentazione.  

Esempi:

- ✅ `descrizione`  
- ❌ `descrizione_iva`, `descrizione_cliente`

In caso di più varianti sullo stesso concetto, usare un suffisso chiaro e funzionale:

- `descrizione` / `descrizione_breve`  
- `nome` / `nome_esteso`

> ℹ️ Le convenzioni sono tratte dalla struttura condivisa in Zero ERP

### 3. Gestione delle Chiavi Primarie

1. **UUID** per entità master (anagrafiche.soggetti):

   ```sql
   id UUID PRIMARY KEY
     DEFAULT uuidv7()
   ```
2. **Serial/Identity** per tabelle tecniche e di relazione:

   ```sql
   id SERIAL PRIMARY KEY
   -- o
   id INTEGER GENERATED BY DEFAULT AS IDENTITY
   ```
3. **Sequenze** esplicite quando serve:

   * Creazione: `CREATE SEQUENCE schema.table_id_seq START 1;`
   * Colonna: `defaultValueComputed: "nextval('schema.table_id_seq'::regclass)"`
   * Oppure `autoIncrement: true` per delegare a Liquibase/DB

---

### 4. Eccezioni e Alternative

* **UUID vs SERIAL**: usare UUID quando serve unicità globale o sharding; SERIAL su tabelle di log e storicizzazione.
* **Foreign Key con composti**: preferire surrogate key (`id`) e colonne FK (`<table>_id`) piuttosto che chiavi composte.
* **Campi tecnici**: evitare prefissi in `dbops`; usare solo `vw_...` e `fn_...` per uniformità

### 5. Trigger e Funzioni

* **Trigger Functions** :

**Naming delle trigger function:**

Qui la scelta migliore è NON mettere né fase né eventi nel nome della funzione.

Quindi:

**trgfn_<schema_opzionale>_<tabella>_<descrizione_breve>**
```
Esempi:

trgfn_anagrafiche_soggetti_tx_id_managed

trgfn_vendite_ddt_righe_qta_from_operativa

trgfn_config_stati_prevent_delete_if_used

```
**Utilizzo di check o guard**

* A. Usa check per funzioni “pure” che verificano

  Funzioni che:
  prendono input restituiscono boolean (o un codice)
  non fanno RAISE EXCEPTION da sole

  Esempi:
  fn_check_codice_fiscale(formato text) RETURNS boolean
  fn_check_piva(formato text, stato text) RETURNS boolean

  Queste le usi dentro altre funzioni/trigger per decidere cosa fare.

* B. Usa guard per funzioni che bloccano (fail-fast)

Funzioni che:
  chiamano eventualmente fn_log_and_raise_error(...)
  fanno da “sentinella”: se la condizione non è rispettata → alzano errore
  normalmente restituiscono void o al massimo un boolean che quasi non guardi mai

  Esempi:

  fn_guard_codice_fiscale(formato text)
  fn_guard_piva(formato text, stato text)

**Cosa non fare:**

Mescolare i nomi a caso:

  una volta fn_check_* che fa RAISE
  una volta fn_guard_* che torna boolean

  Diventa impossibile capire dal nome se la funzione lancia o verifica soltanto.

### 6b. Riferimenti esterni a tabelle di catalogo (chiave naturale stabile)

**Principio**. Qualunque parametro, seed, configurazione esterna o riferimento applicativo che punti a una tabella di catalogo DEVE referenziarla per **chiave naturale stabile**, non per id numerico. L'id e' dettaglio implementativo soggetto a reseed/cancellazione e ricreazione; la chiave naturale stabile e' il contratto cross-ambiente.

**Cos'e' una chiave naturale stabile** (ordine di preferenza):

1. **`codice_interno`** se la tabella la espone — e' la convenzione standard del progetto, immutabile via `script.trgfn_lock_columns` provisionato automaticamente da `dbops.fn_run_automations_lock_columns` (la sola presenza della colonna `codice_interno` provisiona il lock; nessuna riga in `dbops.automation_lock_columns` necessaria).
2. **Codici ISO** dove pertinente: `code_iso2`, `code_iso3` (stati), `currency_code` (valute), ecc. — chiavi naturali esterne all'ERP, definite da standard pubblici e quindi gia' stabili per costruzione.
3. **Altra colonna di catalogo immutabile per design** (es. `codice` quando documentato non riassegnabile e protetto da lock). Caso da motivare nella PR.

**Vietato** referenziare via id integer/bigint quando la tabella espone una di queste chiavi.

**Implementazione**.

* **Per parametri in `config.parameters` e `config.parameter_overrides`**: la regola si applica via il framework FK-surrogata (registry `config.parameter_fk_surrogate` + dispatcher `config.trgfn_parameters_fk_surrogate_dispatch` su `parameters` + dispatcher speculare su `parameter_overrides`). Aggiungere un nuovo pattern non richiede nuovo codice DB: una riga seed nel registry collega `code_pattern` (EXACT o LIKE) a `target_schema.target_table.target_column`. Il dispatcher esegue il check su `default_value` (parameters) e su `overridden_value` (overrides) tramite `script.fn_check_parameter_fk_surrogate`. Errori sollevati: `E_PARAMETER_DEFAULT_VALUE_INVALID` (id 422) sul default, `E_PARAMETER_OVERRIDE_VALUE_INVALID` (id 423) sull'override.
* **Per altri riferimenti esterni** (es. file di configurazione, payload API, JSONB): stesso principio applicato via guard ad-hoc o validazione in service-layer; documentare nel manuale del consumer.

**Esempi consolidati**:

| Referenza | Pattern code | Target |
| --- | --- | --- |
| `DEFAULT_TIPO_SOGGETTO_DETTAGLIO_<RUOLO>` (es. `_CL`, `_FO`) | LIKE `DEFAULT_TIPO_SOGGETTO_DETTAGLIO_%` | `config.tipi_soggetto_dettaglio.codice_interno` |
| `DEFAULT_UTILITY` | EXACT | `config.utilities.codice_interno` |
| `state_code_iso3` (default ISO3 stati) | — (parametro single-shot, no pattern) | `config.stati.code_iso3` (chiave naturale ISO) |
| `soggetto_default_stato_iso2` | — | `config.stati.code_iso2` |

**Tech debt riconosciuto**: parametri legacy che oggi stoccano id numerici a tabelle di catalogo che **non espongono ancora** una chiave naturale stabile (es. `DEFAULT_IVA_ID` -> `config.iva.id`). Restano fuori scope del framework finche' la tabella target non viene dotata della chiave (aggiungere `codice_interno` -> il lock automatico viene provisionato dal runner -> rinominare il parametro -> aggiungere riga al registry). Migrazione tracciata caso per caso, non bulk.

**Override del principio**: ammessi solo in casi documentati (es. join interni cross-schema con vincoli di performance, FK fisica reale dove il reseed non e' possibile). Va motivato nella migration o nel manuale.

### 7b. Validita` temporale (`daterange` nativo)

Le tabelle con validita` temporale usano il pattern **colonne input + colonna range STORED generated**:

| Colonna | Tipo | Scopo |
| --- | --- | --- |
| `valido_dal` | `DATE NOT NULL` | Data inizio validita` (input utente/API) |
| `valido_al` | `DATE NULL` | Data fine validita` (input utente/API, NULL = aperto) |
| `validita` | `daterange GENERATED ALWAYS STORED NOT NULL` | Range calcolato automaticamente da valido_dal/valido_al |

**DDL standard** (PostgreSQL 18+):

```sql
valido_dal DATE NOT NULL,
valido_al  DATE,
validita   daterange GENERATED ALWAYS AS (
               daterange(COALESCE(valido_dal, '-infinity'::date),
                         COALESCE(valido_al,  'infinity'::date), '[]')
           ) STORED NOT NULL,
```

**Regole**:

* `validita` e` **STORED generated**: calcolata automaticamente da PG ad ogni INSERT/UPDATE su `valido_dal`/`valido_al` — mai scrivibile direttamente
* Non e` necessario nessun trigger per mantenerla aggiornata
* Nei **BEFORE trigger** `NEW.validita` e` **NULL** (la generazione avviene dopo tutti i BEFORE trigger). Per calcolare il range del nuovo valore usare **con COALESCE simmetrico** all'espressione STORED:

  ```sql
  daterange(
      COALESCE(NEW.valido_dal, '-infinity'::date),
      COALESCE(NEW.valido_al,  'infinity'::date),
      '[]'
  )
  ```

  **Motivazione**: `daterange(d, NULL, '[]')` produce `upper_inf=true` (testo: `[d,)`), mentre la STORED con COALESCE produce `upper_inf=false, upper='infinity'::date` (testo: `[d,infinity]`). L'operatore `@>` confronta le rappresentazioni interne: `[d,infinity] @> [d,)` restituisce **false** anche se semanticamente equivalenti. Applicare COALESCE garantisce rappresentazioni identiche e `@>` corretto.
* Per tabelle con colonne sorgente diverse (es. `data_inizio`/`data_fine`): colonna STORED con espressione adattata
* Per `TIMESTAMPTZ` usare `tstzrange` con bounds `[)` e colonna STORED adattata

**Naming**:

| Contesto | Nome colonna range |
| --- | --- |
| Colonne `valido_dal`/`valido_al` | `validita` |
| Colonne dominio-specifiche (es. `data_inizio`/`data_fine`) | Nome dominio (es. `periodo_sospensione`, `periodo_calcolo`) |

**Query**:

```sql
-- Containment (data nel range)
WHERE validita @> CURRENT_DATE

-- Overlap (due range si sovrappongono)
WHERE validita && other_range
```

**Vincoli anti-overlap** (due pathway, scegliere in base alla presenza di `WHERE`):

```sql
-- Pathway 1: senza WHERE → temporal UNIQUE PG 18 (preferito, SQL:2011 standard)
-- L'indice GiST generato dal constraint serve anche query WHERE validita @> data
ALTER TABLE schema.tabella
    ADD CONSTRAINT uq_tabella_no_overlap
    UNIQUE (key_col, validita WITHOUT OVERLAPS);

-- Pathway 2: con WHERE → EXCLUDE USING gist parziale (unico tipo che enforça
-- con predicato parziale; il temporal UNIQUE PG18 non supporta WHERE).
-- DEVE essere un ADD CONSTRAINT ... EXCLUDE, NON un CREATE INDEX:
-- un CREATE INDEX ... USING gist (key_col, validita) NON enforça nulla (e' solo
-- una struttura di supporto query). Richiede l'estensione btree_gist.
ALTER TABLE schema.tabella
    ADD CONSTRAINT ex_tabella_no_overlap
    EXCLUDE USING gist (key_col WITH =, validita WITH &&)
    WHERE (attivo IS TRUE);
```

> perdendo silenziosamente l'enforcement (nome `ex_*` identico). Vedi
> `dev/work-done/refactor-overlap.md`. Un `CREATE INDEX ... USING gist`
> **non enforça mai**: per un anti-overlap serve sempre un `ADD CONSTRAINT ...
> EXCLUDE`.

> framework: vedi `dev/work-done/refactor-overlap-v2.md` (Fase 2).

**Entita' con stati annullabili (`UNIQUE WITHOUT OVERLAPS` + `is_abortito`):**

Quando una tabella usa **Pathway 1** e ha stati che transitano a `is_abortito = true`
(es. ANNULLATO), le righe abortite partecipano al constraint di overlap bloccando
nuovi record sulla stessa chiave.

**Nota PG18**: `'empty'::daterange` non e' ammesso come valore nel temporal part di
`UNIQUE WITHOUT OVERLAPS` — ne' in fase di `ADD CONSTRAINT` ne' su INSERT/UPDATE
successivi. Non e' possibile "escludere" righe con un range vuoto.

**Soluzione**: migrare da `UNIQUE WITHOUT OVERLAPS` (Pathway 1) a `EXCLUDE USING gist`
parziale (Pathway 2) con predicato `WHERE (NOT is_abortito_snapshot)`.

1. **Colonna denormalizzata** `is_abortito_snapshot BOOLEAN NOT NULL DEFAULT false`
   — snapshot di `<tabella_stati>.is_abortito` sulla stessa riga (necessaria perche'
   i constraint non possono referenziare altre tabelle).

2. **BEFORE trigger** (fase `_z90_`, evento `INSERT OR UPDATE OF <col_stato>`)
   — mantiene `is_abortito_snapshot` aggiornato. Deve essere BEFORE (non AFTER):
   nelle BEFORE trigger chain PG aggiorna NEW prima di scrivere la riga; un AFTER
   trigger non puo' influenzare il predicato WHERE valutato al momento dell'INSERT.

3. **Swap del constraint**: drop `UNIQUE WITHOUT OVERLAPS`, add `EXCLUDE USING gist`
   con `WHERE (NOT is_abortito_snapshot)`. Richiede `btree_gist` per le colonne
   di uguaglianza non-range. La colonna `validita` originale resta invariata.

```sql
-- Step 1: colonna snapshot + backfill
ALTER TABLE schema.tabella
    ADD COLUMN is_abortito_snapshot BOOLEAN NOT NULL DEFAULT false;
UPDATE schema.tabella t
   SET is_abortito_snapshot = s.is_abortito
  FROM config.stati_doc_<entita> s
 WHERE s.id = t.stato_doc_<entita>_id;

-- Step 2: BEFORE trigger (vedere naming convention trigger)

-- Step 3: swap constraint
ALTER TABLE schema.tabella
    DROP CONSTRAINT uq_tabella_no_overlap;
ALTER TABLE schema.tabella
    ADD CONSTRAINT ex_tabella_no_overlap
    EXCLUDE USING gist (
        key_col_1 WITH =,
        key_col_2 WITH =,
        validita  WITH &&
    )
    WHERE (NOT is_abortito_snapshot);
```

Righe abortite escluse dal predicato `WHERE`: non partecipano al check di overlap.
`dbops.automazione_overlap` deve restare `active = false` per la tabella
(il constraint parziale non e' gestibile dal framework standard).

> Prima applicazione: `vendite.contratti`, migration `20260521-01..03`.

**Temporal FK** (PG 18, solo se padre ha temporal UNIQUE):

```sql
-- Prerequisito: padre deve avere UNIQUE (id, validita WITHOUT OVERLAPS)
ALTER TABLE schema.figlio
    ADD CONSTRAINT fk_figlio_padre_temporal
    FOREIGN KEY (padre_id, PERIOD validita)
    REFERENCES schema.padre (id, PERIOD validita);
```

Per la gestione automatizzata degli EXCLUDE con WHERE: `dbops.automazione_overlap` e `dbops.fn_apply_automazione_overlap`.

> Riferimento: `docs/it/dev/work-done/piano-miglioramenti-db-pg18.md` per verifica empirica (STORED generated, temporal UNIQUE/FK) e piano di migrazione.

### 7c. Ciclo stato + finestra di validita`

Quando una tabella ha **sia** una colonna `stato` (ciclo vita gestionale: es. `BOZZA` / `ATTIVA` / `CHIUSA`) **sia** un intervallo `valido_dal`/`valido_al` (o `validita` daterange), valgono queste regole.

**Principio fail-safe: le date comandano, lo stato discrimina operativo da preparazione.**

1. **Applicabilita' operativa = date + whitelist stati operativi**. I lookup di business e i filtri di efficacia usano `attivo = TRUE AND stato IN (<lista_operativi>) AND validita @> data_riferimento`. La lista degli stati operativi e' dichiarata nella doc manuale della tabella. Questa regola vale per le tabelle che hanno stati di **preparazione** (es. `BOZZA`) che condividono volutamente date sovrapposte con stati operativi (es. workflow clone+publish per `listini_versioni`). Per tabelle senza stati di preparazione, lo stato e' solo gestionale e il filtro `stato` puo' essere omesso dai lookup operativi.

   **Whitelist vs blacklist**: preferire `stato IN ('ATTIVA','CHIUSA')` a `stato != 'BOZZA'`; la whitelist esplicita non include automaticamente futuri stati intermedi.

2. **`stato` = workflow gestionale**. Transizioni governate dall'utente e vincolate da un guard trigger (`trgfn_<tabella>_guard_transizione_stato`, fase `_a10_`, `BEFORE UPDATE OF <col_stato>`). Lo stato serve a UI, audit, reportistica, dashboard — e per distinguere stati di preparazione da stati operativi (punto 1).
3. **Transizione verso lo stato terminale**: la regola del guard puo' includere una **precondizione temporale** (`valido_al IS NOT NULL AND valido_al < CURRENT_DATE`) per evitare incoerenze strutturali (stato "chiuso" con finestra ancora aperta). Stessa regola vale per l'utente (via API/service) e per il job di sync.
4. **Sync stato -> data**: il framework parametrico **`dbops.fn_apply_chiusura_scadenze()`** + job pgAgent unico **`chiusura_scadenze_daily`** (00:05) esegue l'UPDATE massivo `stato = terminale` per le righe scadute (`valido_al < CURRENT_DATE`) su tutte le tabelle configurate. L'UPDATE attraversa il guard trigger e lo soddisfa per costruzione. Vedi sotto "Framework dbops.automazione_chiusura_scadenze".
5. **Niente trigger di sync `valido_al` -> `stato`** e nessuna colonna generata: lo stato **non e'** derivato in tempo reale dalla data (es. l'utente puo' programmare `valido_al` futuro e lo stato resta ATTIVA finche' il job non scatta). La sincronizzazione e' asincrona e "cosmetica".
6. **INSERT**: non vincolare l'INSERT con la matrice transizioni (per permettere seed/import con stati diretti). Il guard scatta solo su UPDATE OF stato.
7. **Semantica `valido_al`**: ultimo giorno **incluso** (convenzione `script.trgfn_set_validita`, bounds <code>[]</code> canonicalizzati a <code>[)</code>). Esempio: `valido_al = 2026-04-26` → la riga e' operativamente valida fino al 2026-04-26 23:59:59, scade dal 2026-04-27. Conseguenza: la query `valido_al < CURRENT_DATE` chiude **dal giorno successivo** a `valido_al` — schedule 00:05 cattura al primo momento utile dopo il cambio data.

#### Framework `dbops.automazione_chiusura_scadenze` (post 26-04-2026)

La logica di chiusura per scadenza e' centralizzata in un framework parametrico. Aggiungere una nuova tabella al pattern non richiede nuovo codice DB: basta una INSERT seed nella tabella di configurazione.

| Componente | Posizione | Ruolo |
| --- | --- | --- |
| Tabella config | `dbops.automazione_chiusura_scadenze` | Una riga per tabella target (schema, nome, colonna stato, codici attivo/chiuso, etc.) |
| Funzione motore | `dbops.fn_apply_chiusura_scadenze()` | SQL dinamico con pre-check + dispatch VARCHAR/FK + audit + JSONB risultato |
| Job unico | `chiusura_scadenze_daily` (`85_pgagent/`) | Schedule 00:05, esegue la fn |

**Tipologie supportate** (colonna `tipo_stato`):

* **VARCHAR**: `stato` e' colonna varchar diretta + CHECK constraint. Esempio `vendite.listini_versioni` con `stato IN ('BOZZA','ATTIVA','CHIUSA')`.
* **FK**: `stato` e' FK a tabella catalogo, codici espressi come `codice_interno` (immutabile per `lock_columns`). Esempio `vendite.contratti.stato_doc_contratto_id` -> `config.stati_doc_contratti`.

**Esempio righe seed** (`80_data/sql/dbops/automazione_chiusura_scadenze.csv`):

```csv
schema_tabella,nome_tabella,col_stato,tipo_stato,stato_attivo_codice,stato_chiuso_codice,fk_lookup_schema,fk_lookup_table
vendite,listini_versioni,stato,VARCHAR,ATTIVA,CHIUSA,,
vendite,contratti,stato_doc_contratto_id,FK,ATTIVO,CESSATO,config,stati_doc_contratti
```

#### Componenti tabella-specifici (NON generalizzati nel framework)

Restano sotto la responsabilita' del dominio:

* Trigger guard transizione (matrice transizioni ammesse, codici stato, messaggi errore tipati)
* Codice errore dedicato in `config.messaggi_errore` (es. `E_VERSIONE_STATO_TRANSIZIONE_INVALIDA`, `E_CONTRATTO_STATO_TRANSIZIONE_INVALIDA`)
* Documentazione manuale della tabella

La generalizzazione del guard transizione e' rinviata: serviranno almeno tre casi reali con strutture transizione affini per giustificare l'astrazione (manifesto sviluppo concentrico §7).

**Casi gia' applicati**:

* `vendite.listini_versioni` (VARCHAR, ciclo `BOZZA -> ATTIVA -> CHIUSA`)
* `vendite.contratti` (FK, ciclo `DRAFT -> ATTIVO -> CESSATO`; `SOSPESO` esiste come codice ma fuori scope)

**Riferimento**: `docs/it/dev/work-done/automazione-chiusure-scadenze.md`.

### 8. Indici

* **Naming**: `ix_<table>_<column>`
* **Tipologia**: B-Tree per default; GIN/GIST per JSONB/Geometrie.
* **Parziali**: `CREATE UNIQUE INDEX ix_contatti_default ON contatti(soggetto_id) WHERE is_default;` per default logic
* **Indici `upper(...)`**: non usarli in modo generico; introdurli solo per query case‑insensitive specifiche e con beneficio prestazionale misurabile.
* **Ricerche case‑insensitive**: usare `ILIKE` lato query; l’indice serve solo se compatibile con la forma del predicato.

---

### 9. Automazione Indici FK

All’interno della cartella **`90_end/`** delle migrazioni Liquibase, inserire sempre per ultimi uno script YAML con `runAlways` o `runAlways: false` per richiamare la procedura che crea/rimuove indici sulle foreign key:

```yaml
- changeSet:
    id: 90-end-apply-fk-policy
    author: mctit
    runAlways: true
    sql:
      splitStatements: false
      sql: |
        CALL dbops.apply_fk_index_policy();
```

* La tabella `dbops.fk_index_policy` deve essere mantenuta aggiornata:

  * individuare nuove FK senza indice con `dbops.vw_fk_senza_indice`
  * popolare policy con `SELECT dbops.fn_populate_fk_index_policy();`
* La policy consente di generare o eliminare indici non necessari.

### 10. Gestione Indici Duplicati

Utilizzare la view **`dbops.vw_duplicate_indexes`** per visualizzare gli indici che condividono lo stesso insieme di colonne e razionalizzare la struttura:

```sql
SELECT *
  FROM dbops.vw_duplicate_indexes;
```


## 8. Indici

Gli indici rappresentano uno strumento fondamentale per garantire performance, scalabilità e prevedibilità delle query in Zero ERP.
Devono essere progettati secondo regole uniformi, evitando proliferazioni inutili e mantenendo coerenza con i pattern applicativi.

---

### 8.1 Naming

**Convenzione generale:**

```
ix_<table>_<column>
```

Esempi:

* `ix_contatti_soggetto`
* `ix_soggetti_codice`

Per indici specializzati:

| Tipologia      | Naming                             |
| -------------- | ---------------------------------- |
| pg_trgm        | `ix_<table>_<column>_trgm`         |
| FTS (tsvector) | `ix_<table>_<column>_fts`          |
| Parziale       | `ix_<table>_<column>_<condizione>` |

Se l’indice è applicato a una colonna normalizzata, è consigliato esplicitarlo nel nome:

```
ix_soggetti_ragione_sociale_norm_trgm
```

---

### 8.2 Tipologie

| Tipo   | Uso consigliato                     |
| ------ | ----------------------------------- |
| B-Tree | Default per =, ORDER BY, range, FK  |
| GIN    | JSONB, FTS, pg_trgm                 |
| GiST   | Geometrie, casi particolari pg_trgm |
| BRIN   | Tabelle molto grandi e append-only  |

⚠️ Non sostituire mai il B-Tree con GIN/GiST: sono complementari, non alternativi.

---

### 8.3 Policy di Ricerca Testuale (pg_trgm e FTS)

Questa policy definisce quando e come usare indici per ricerca testuale e fuzzy in Zero ERP.

#### 8.3.1 Quando usare pg_trgm (GIN)

Utilizzare **GIN + gin_trgm_ops** per colonne che:

* sono ricercate con `ILIKE '%...%'`
* supportano ricerche parziali e refusi
* sono usate come campo principale di ricerca utente

Esempi tipici:

* `anagrafiche.soggetti.ragione_sociale_normalizzata`
* `config.stradario_generale.indirizzo_normalizzato`
* denominazioni, titoli brevi, riferimenti descrittivi

Indice standard:

```
CREATE INDEX ix_<table>_<column>_trgm
ON <schema>.<table>
USING gin (<column> gin_trgm_ops);
```

#### 8.3.2 Quando NON usare pg_trgm

Non usare pg_trgm su:

* identificativi strutturati: P.IVA, CF, POD/PDR
* codici documento
* campi tecnici o enumerativi

Per questi casi preferire:

* B-Tree
* UNIQUE

#### 8.3.3 Colonne normalizzate

Gli indici pg_trgm devono preferibilmente essere applicati su colonne **normalizzate**:

* lowercase
* spazi singoli
* punteggiatura rimossa

Esempio naming:

```
ragione_sociale_normalizzata
indirizzo_normalizzato
```

Questo garantisce:

* maggiore qualità dei risultati
* stabilità delle query
* maggiore riutilizzo dell’indice

---

#### 8.3.4 Full Text Search (FTS)

Utilizzare FTS solo per:

* testo libero
* descrizioni lunghe
* note, commenti, pratiche

Pattern consigliato:

* colonna `tsvector` dedicata
* indice GIN

```
descrizione_fts tsvector

CREATE INDEX ix_<table>_descrizione_fts
ON <schema>.<table>
USING gin (descrizione_fts);
```

⚠️ Non usare FTS per:

* codici
* filtri di business
* dati strutturati

---

#### 8.3.5 GIN vs GiST per pg_trgm

Scelta consigliata:

| Motivo                         | Scelta                        |
| ------------------------------ | ----------------------------- |
| Ricerca contains/fuzzy         | GIN                           |
| Massime performance in lettura | GIN                           |
| Minore spazio / meno write     | GiST (valutare con benchmark) |

👉 In Zero ERP la scelta predefinita è **GIN**.

---

#### 8.3.6 Parametri GIN

I parametri vanno impostati solo se motivati:

| Parametro              | Quando usarlo                  |
| ---------------------- | ------------------------------ |
| fastupdate             | Tabelle molto scritte          |
| gin_pending_list_limit | Bulk insert o flussi intensivi |

In assenza di esigenze specifiche, usare i default.

---

#### 8.3.7 Regole UI / Servizi

Per rendere efficaci gli indici pg_trgm:

* imporre minimo 3 caratteri per la ricerca fuzzy
* per query < 3 caratteri usare:

  * prefissi (B-tree)
  * suggerimenti

---

### 8.4 Indici Parziali

Usare indici parziali per:

* logica di default
* flag booleani

Esempio:

```
CREATE UNIQUE INDEX ix_contatti_default
ON contatti(soggetto_id)
WHERE is_default;
```

---

### 8.5 Case-Insensitive

Evitare indici su `upper()` o `lower()` se non motivati.
Preferire:

* colonne normalizzate
* predicati compatibili con la forma dell’indice

---

### 8.6 Gestione Indici Duplicati

Utilizzare la view:

```
SELECT *
FROM dbops.vw_duplicate_indexes;
```

per razionalizzare la struttura e prevenire overhead inutili.

---

### 8.7 Automazione Indici FK

Gli indici sulle FK sono gestiti tramite policy centralizzata.

Nel changelog `90_end/` deve essere presente:

```yaml
- changeSet:
    id: 90-end-apply-fk-policy
    author: mctit
    runAlways: true
    sql:
      splitStatements: false
      sql: |
        CALL dbops.apply_fk_index_policy();
```

La tabella `dbops.fk_index_policy` governa:

* quali FK indicizzare
* quali escludere

La view di supporto:

```
SELECT * FROM dbops.vw_fk_senza_indice;
```

### 9. Transaction ID Centralizzato

Per garantire **coerenza transazionale** fra tutte le tabelle che registrano modifiche, ogni entità deve avere la colonna `tx_id UUID` che accetta anche valori nulli:

* **Trigger (opzione DB)**: applicare `trg_assign_tx_id` (su ogni tabella) che utilizza la function `dbops.trgfn_tx_id_managed()` per generare o recuperare il `tx_id` di sessione.
* **Function (opzione backend)**: invocare `dbops.fn_get_or_create_session_tx_id()` prima delle operazioni e passare il `tx_id` in tutti gli `INSERT/UPDATE`.

Per maggiori dettagli e implementazione, consulta la guida **(è fondamentale la consultazione)**:
**[Guida Tecnica – Implementazione di un Unico Transaction ID](/guide/tx_id_implementation_guide)**

### 10. Row Level Security (RLS)

> **Scheda tecnica PostgreSQL**: [row-level-security](/postgresql/row-level-security) — sintassi,
> troubleshooting, performance, interazione con viste e funzioni `SECURITY DEFINER`.

Le policy RLS sono il meccanismo nativo PostgreSQL per filtrare **quali righe** un utente vede
o puo' modificare. In ZeroErp sono lo strumento **di difesa in profondita'** sullo scope dati
multi-utente (operatori, clienti portale, fornitori portale, shop customer).

#### 10.1 Quando usarla

Abilitare RLS **solo** su tabelle con scope multi-soggetto, ovvero tabelle le cui righe
appartengono a piu' entita' distinte che non devono vedersi tra loro:

* **Multi-tenant / multi-emittente**: tabelle con `emittente_soggetto_ruolo_id` o simili,
  dove un operatore e' limitato dalla whitelist `config.user_emittenti_fiscali`.
* **Multi-cliente**: tabelle operazionali (fatture, scadenze, DDT) dove un
  `CLIENTE_PORTALE` deve vedere solo i propri billing account.
* **Multi-fornitore**: ordini ricevuti, pagamenti verso il fornitore.
* **Self-ownership**: tabelle shop dove uno `SHOP_CUSTOMER` vede solo i propri dati.

**Non** abilitare RLS su:

* Tabelle di configurazione lette da tutti (parametri, lookup, enum).
* Tabelle di sola scrittura tecnica (`dbops.*`, log, storico gia' filtrato a monte).
* Tabelle che non hanno una relazione diretta e verificabile con l'utente corrente.

Se una tabella non ha uno scope evidente, probabilmente **non va messa in RLS**: aggiungere
policy "preventive" genera falsa sicurezza e costo di manutenzione.

#### 10.2 Naming policy

```
rls_<tabella>_<nome_scope>
```

Esempi:

* `rls_fatture_ba_ownership` — cliente portale vede solo fatture dei propri billing account
* `rls_ordini_fornitore_ownership` — fornitore vede solo ordini a lui destinati
* `rls_fatture_ef_whitelist` — operatore vede solo emittenti della propria whitelist
* `rls_ordini_shop_self_ownership` — shop customer vede solo ordini propri

**Regole**:

* Una tabella puo' avere **piu'** policy concorrenti (una per scope). PostgreSQL le combina in
  OR per evento `SELECT/UPDATE/DELETE` (piu' permissivo vince).
* Se servono semantiche diverse su `SELECT` vs `UPDATE`, creare policy distinte con
  `FOR SELECT` / `FOR UPDATE` esplicito, **mai** policy `FOR ALL` generiche.
* Il nome deve rendere leggibile la combinazione tabella + regola di scope.

#### 10.3 Logica di scope in funzioni `script.fn_scope_*`

**Regola tassativa**: la condizione della policy deve invocare una funzione del pattern
`script.fn_scope_<nome_scope>(...)` che ritorna `boolean`. **Non** scrivere logica inline
nella policy.

Motivazioni:

* **Testabilita' pgTAP**: la funzione e' chiamabile singolarmente con dati sintetici,
  quindi copribile con test isolati senza ricorrere a `SET ROLE` di simulazione.
* **Riuso**: la stessa funzione puo' essere usata in viste di supporto, controlli applicativi
  e altre policy.
* **Leggibilita'**: la policy resta leggera e auto-documentante.

Firma consigliata:

```sql
CREATE FUNCTION script.fn_scope_ba_ownership(
    p_identita_id          BIGINT,
    p_billing_account_id   BIGINT
) RETURNS BOOLEAN
LANGUAGE sql
STABLE
AS $$ ... $$;
```

Policy che la usa:

```sql
CREATE POLICY rls_fatture_ba_ownership ON vendite.fatture
    FOR SELECT
    USING (
        script.fn_scope_ba_ownership(
            current_setting('app.current_identita_id', true)::bigint,
            billing_account_id
        )
    );
```

#### 10.4 Input: sempre dai GUC `app.*`

Le funzioni `fn_scope_*` non devono mai dedurre l'utente corrente da `session_user` o
`current_user` del DB. L'utente "applicativo" non coincide con il ruolo DB: il backend si
connette al DB con un ruolo tecnico (`zeroerp_app`) e propaga l'identita' applicativa
tramite GUC (vedi [parametri-personalizzati-GUC](/postgresql/parametri-personalizzati-(GUC))).

GUC di riferimento:

| GUC | Significato |
| --- | --- |
| `app.current_user_id` | `auth_user.id` Django dell'utente autenticato |
| `app.current_identita_id` | id del record attivo in `anagrafiche.identita_digitali` |
| `app.ruolo_applicativo` | ruolo applicativo corrente (OPERATORE, CLIENTE_PORTALE, ...) |
| `app.soggetto_ruolo_id` | `soggetti_ruoli.id` dell'identita' corrente |

La policy chiama la funzione passando i GUC, **mai** leggendoli dentro la funzione — questo
mantiene la funzione pura e testabile con input espliciti.

`current_setting('app.xxx', true)` ritorna stringa vuota se il GUC non e' settato.
Gestire il fallback con `NULLIF(..., '')::bigint` o un guard esplicito nel caller.

**Helper `script.fn_current_identita_context()`** — per leggere i tre GUC multi-face-auth
(`app.current_identita_id`, `app.ruolo_applicativo`, `app.soggetto_ruolo_id`) in un unico
`SELECT` tipato, usare il wrapper
[`script.fn_current_identita_context`](/dbzero/script/funzioni/fn_current_identita_context).
Utile dentro funzioni PL/pgSQL che necessitano piu' di un campo di contesto:

```sql
DECLARE
    v_ctx   record;
BEGIN
    SELECT * INTO v_ctx FROM script.fn_current_identita_context();
    IF v_ctx.current_identita_id IS NULL THEN
        RETURN false;  -- fail-closed: sessione senza identita
    END IF;
    -- ... usa v_ctx.current_identita_id, v_ctx.ruolo_applicativo, ecc.
END;
```

Dentro una policy RLS e' comunque preferibile leggere **solo** il GUC effettivamente usato
(es. `app.current_identita_id`) per evitare chiamata funzione non necessaria.

#### 10.5 Bypass per ruoli DB di manutenzione

Alcuni ruoli DB devono poter bypassare le policy per eseguire migrazioni, analisi e
riparazioni dati. Due strategie complementari:

1. **`BYPASSRLS` sul ruolo** (preferito per ruoli tecnici dedicati):

   ```sql
   ALTER ROLE zeroerp_admin      BYPASSRLS;
   ALTER ROLE zeroerp_migration  BYPASSRLS;
   ```

   Il ruolo ignora tutte le policy. Superuser ha `BYPASSRLS` per default.

2. **`FORCE ROW LEVEL SECURITY`** sulla tabella per **estendere** RLS anche al proprietario
   della tabella (altrimenti esentato):

   ```sql
   ALTER TABLE vendite.fatture FORCE ROW LEVEL SECURITY;
   ```

   Usare **sempre** `FORCE` quando la tabella e' di proprieta' di un ruolo applicativo
   (`zeroerp_app`): altrimenti l'owner non vede le policy e la RLS e' aggirata per sbaglio.

3. **`zeroerp_app` NON deve avere `BYPASSRLS`**: e' il ruolo con cui il backend si
   connette, deve essere soggetto a tutte le policy.

#### 10.6 `USING` vs `WITH CHECK`

Due clausole distinte, con semantica diversa:

| Clausola | Quando | Cosa verifica |
| --- | --- | --- |
| `USING` | SELECT, UPDATE, DELETE | Righe **esistenti** visibili al comando |
| `WITH CHECK` | INSERT, UPDATE | Righe **nuove / modificate** ammesse a scriversi |

**Regole pratiche**:

* Su `FOR SELECT` basta `USING`.
* Su `FOR INSERT` serve solo `WITH CHECK` (non si selezionano righe "esistenti").
* Su `FOR UPDATE` servono **entrambe**: `USING` controlla cosa l'utente puo' toccare,
  `WITH CHECK` impedisce di "spostare" una riga fuori dal proprio scope
  (es. un cliente che modifica `billing_account_id` per rubare una fattura).
* Se `WITH CHECK` e' omesso su UPDATE, PostgreSQL usa `USING` anche per la verifica post-update
  — spesso non e' quello che serve. **Esplicitare sempre** `WITH CHECK` per evitare ambiguita'.

#### 10.7 Defense-in-depth, non sostituzione

Le policy RLS **si sommano** ai filtri applicativi esistenti (`EmittenteFiscaleScopeMixin`,
filtri repository, `ZeroERPPermission`), **non li rimpiazzano**.

| Livello | Cosa controlla | Dove |
| --- | --- | --- |
| Permission | Se l'utente puo' chiamare l'endpoint | Django DRF |
| Filtro queryset | Filtri di business (stato, periodo, tipo) | Repository/service |
| **RLS** | **Righe effettivamente visibili** | **PostgreSQL** |

Regola: **se un filtro applicativo si dimentica, la RLS salva. Se la RLS e' troppo
restrittiva, il bug e' evidente subito.** Mai il contrario.

#### 10.8 Test pgTAP obbligatori

Per ogni policy RLS pushata in produzione devono esistere test pgTAP che coprono:

1. **Utente autorizzato vede le sue righe** (GUC settato su identita' proprietaria).
2. **Utente non autorizzato non vede righe altrui** (GUC settato su altra identita').
3. **Senza GUC** la policy deve fallire "chiusa" (nessuna riga) oppure esplicitamente aperta
   solo per ruoli bypass.
4. **Ruolo `BYPASSRLS` vede tutto** (regression).
5. **`WITH CHECK` blocca** update/insert fuori scope (se applicabile).

Naming file test: `db/pgtap/rls/<schema>_<tabella>_rls.sql`.

#### 10.9 Checklist migrazione

Prima di attivare RLS su una tabella esistente:

* Funzione `script.fn_scope_*` scritta e coperta da pgTAP
* Backend popola tutti i GUC necessari in tutte le auth class
* Benchmark `EXPLAIN` su query principali pre/post attivazione
* Indici funzionali su colonne usate nella policy, se `EXPLAIN` lo richiede
* Ruolo `zeroerp_migration` ha `BYPASSRLS`
* `FORCE ROW LEVEL SECURITY` se la tabella e' owned da `zeroerp_app`
* Policy testata in staging con dati realistici prima del merge
