# Brief Team DB — Anticipo `documenti.documenti_generati_eventi` da Fase B a v1

**Data:** 2026-05-03
**Riferimento:** `sviluppo-documenti.md` §5.12 + §10-bis.5 + Decisione 76; `sviluppo-documenti-db.md` (Fase B)
**Branch:** `dev/db-tid`
**Priorita':** alta (sblocca PR-A backend documenti v1)

---

## Contesto

Lo sviluppo backend documenti v1 e' stato pianificato per il dominio
`PREVENTIVO`. Decisione 31 prevede che ogni download del PDF persistente
registri un evento `SCARICATO`, ma il piano DB Fase A non include la
tabella eventi (rinviata a Fase B).

Il backend chiude la decisione 10-bis.5 con **opzione A**: anticipare la
sola tabella `documenti.documenti_generati_eventi` da Fase B a v1, con
DDL append-only + trigger + pgTAP. Coerente con Decisioni 30/31 e con il
pattern di cleanup storage (Decisione 72, evento `STORAGE_ORPHAN`).

## Cosa si chiede al team DB

Una micro-tranche DB autonoma (tabella + trigger + test), pronta prima
della PR-A backend documenti.

## 1. DDL — `documenti.documenti_generati_eventi`

Tabella append-only, append da backend tramite INSERT diretto (no
funzione DB dedicata in v1).

Schema proposto (allineato §5.12 + standard repo):

```sql
CREATE TABLE documenti.documenti_generati_eventi (
    id                     bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    documento_generato_id  bigint NOT NULL
        REFERENCES documenti.documenti_generati(id) ON DELETE RESTRICT,
    evento_tipo            varchar(60) NOT NULL,
    evento_at              timestamptz NOT NULL DEFAULT now(),
    user_id                integer NULL,        -- FK condizionale auth_user.id (vedi §3.4 sviluppo-documenti-db.md)
    esito                  varchar(30) NOT NULL DEFAULT 'OK',
    messaggio              text NULL,
    detail                 jsonb NOT NULL DEFAULT '{}'::jsonb,
    storicizza             boolean NOT NULL DEFAULT false,  -- log: storico OFF (audit nativo nella tabella stessa)
    tx_id                  uuid,
    data_insert            timestamptz NOT NULL DEFAULT now(),
    user_insert            text NOT NULL DEFAULT CURRENT_USER,
    data_update            timestamptz NOT NULL DEFAULT now(),
    user_update            text NOT NULL DEFAULT CURRENT_USER,

    CONSTRAINT chk_documenti_generati_eventi_evento_tipo
        CHECK (evento_tipo IN (
            'GENERATO',         -- emesso al primo render persistente
            'SCARICATO',        -- ogni download del PDF persistente (Decisione 31)
            'STORAGE_ORPHAN',   -- file orfano post-fail commit (Decisione 72)
            'ANTEPRIMA'         -- opzionale, log anteprima esplicita (default OFF lato BE v1)
        )),
    CONSTRAINT chk_documenti_generati_eventi_esito
        CHECK (esito IN ('OK', 'KO', 'WARN')),
    CONSTRAINT chk_documenti_generati_eventi_messaggio_non_vuoto
        CHECK (messaggio IS NULL OR btrim(messaggio) <> '')
);
```

### Indici

- `ix_documenti_generati_eventi_documento_evento_at`
  `(documento_generato_id, evento_at DESC)` — timeline documento;
- `ix_documenti_generati_eventi_evento_tipo` `(evento_tipo)` —
  dashboard/analytics per tipo evento.

FK index su `documento_generato_id` registrata in `dbops.fk_index_policy`
via `dbops.fn_seed_fk_index_policy()` (gia' soddisfatta dal primo indice
composito); FK index su `user_id` da valutare con la policy.

### Note tecniche

- `storicizza = false`: la tabella e' essa stessa il log; non si vuole
  duplicarla in `storico.*`. Disable storico applicativo coerente col
  pattern `documenti.documenti_generati` Fase A (changeset 08 gia'
  applicato).
- `evento_tipo` come `varchar(60)` con CHECK e' coerente con scelta
  Decisione 18 (no ENUM nativi per set non condivisi cross-schema). Il
  set e' estensibile in Fase B (es. `INVIATO`, `ARCHIVIATO`,
  `ANNULLATO`, `RENDER_KO`) modificando il CHECK con migration
  successiva.
- `user_id` NULL: gli eventi tecnici (`STORAGE_ORPHAN`,
  rendering automatici) possono non avere un utente loggato.
- `tx_id`: popolato dal backend per correlare eventi appartenenti alla
  stessa unita' di lavoro (es. `GENERATO` + `STORAGE_ORPHAN`).

## 2. Trigger guard append-only

Tabella append-only: deve consentire solo INSERT. UPDATE e DELETE
vanno bloccati per integrita' della timeline documentale.

### Trigger 1 — block DELETE

```
trgfn_documenti_generati_eventi_a10_block_delete_dlt
```

BEFORE DELETE → `script.fn_log_and_raise_error(...)` con codice errore
parlante (proposta: `E_EVENTO_DOCUMENTO_DELETE_VIETATA`).

### Trigger 2 — block UPDATE

```
trgfn_documenti_generati_eventi_a10_block_update_upd
```

BEFORE UPDATE → `script.fn_log_and_raise_error(...)` con codice errore
(proposta: `E_EVENTO_DOCUMENTO_UPDATE_VIETATA`).

Nessuna eccezione per `user_update`/`data_update`: questi campi servono
solo come default audit a INSERT, ma la tabella non si modifica dopo.

Eventuali correzioni/segnalazioni vengono fatte registrando un evento
ulteriore (es. `WARN` o `KO`) sullo stesso `documento_generato_id`.

## 3. pgTAP atteso

File suggerito: `db/pgtap/documenti/test_documenti_generati_eventi.sql`.

Scenari minimi (10):

1. INSERT `GENERATO` con `esito='OK'` → ammesso.
2. INSERT `SCARICATO` con `user_id` valido → ammesso.
3. INSERT `STORAGE_ORPHAN` con `user_id NULL` + `esito='KO'` →
   ammesso (caso cleanup orfano post-fail commit).
4. INSERT `ANTEPRIMA` → ammesso (set v1 esteso).
5. INSERT `evento_tipo='RENDER_KO'` (non in set v1) → CHECK violato.
6. INSERT `esito='X'` non valido → CHECK violato.
7. INSERT `messaggio=''` (stringa vuota) → CHECK violato.
8. UPDATE `messaggio` su evento esistente → trigger blocca con
   `E_EVENTO_DOCUMENTO_UPDATE_VIETATA`.
9. DELETE evento esistente → trigger blocca con
   `E_EVENTO_DOCUMENTO_DELETE_VIETATA`.
10. FK violata: INSERT con `documento_generato_id` inesistente → 23503
    (FK).

## 6. Cosa NON serve in questa tranche

Per restare nello scope v1 e non sforare:

- nessuna funzione applicativa `fn_register_documento_evento`: il
  backend usa INSERT diretto su tabella, l'integrita' la danno trigger
  + CHECK;
- nessun trigger di propagazione su `documenti_generati` (no auto-evento
  `GENERATO` da DDL): l'evento lo registra il backend dopo commit
  storage + DB testata, per coerenza con il pattern di cleanup;
- nessuna view aggregata: la lettura cronologica usa SELECT diretta con
  ORDER BY `evento_at DESC` (indice gia' previsto).

## 8. Stato lavoro backend dipendente

Il backend e' in attesa di questa tranche per:

- popolare evento `GENERATO` al render persistente (`document_generation_service`);
- popolare evento `SCARICATO` su endpoint download PDF;
- popolare evento `STORAGE_ORPHAN` nel cleanup post-fail commit
  (Decisione 72, `DocumentStorage` + transazione DB);
- esporre eventualmente la timeline come building block lista nelle
  view dominio sorgente (riusabile cross-dominio).

Senza questa tranche, l'opzione di fallback sarebbe non loggare gli
eventi v1, contraddicendo Decisione 31. La preferenza di Tid + team
backend e' anticipare.
