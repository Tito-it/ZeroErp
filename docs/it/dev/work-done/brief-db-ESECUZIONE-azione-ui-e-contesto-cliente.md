## 0. Decisioni di analisi critica (recepite)

1. **Modellazione `azione_ui` → tabella-catalogo + FK** (decisione Tid 2026-06-15).
   Il brief proponeva testo libero "mirror di `handler_key`", ma `handler_key` vive in
   `pratiche.handler_flussi` (catalogo) referenziato via FK `template_flussi.handler_id`.
   Per **simmetria col pattern esistente** e integrità (un typo nel seed fallisce subito,
   non produce un bottone-fantasma) si introduce `pratiche.azioni_ui` + `template_flussi.azione_ui_id`.
2. **Esposizione `billing_account_id` → funzione** `script.fn_get_billing_account_by_istanza`,
   specchio esatto di `script.fn_get_stato_cliente_by_istanza` (stesso schema, stessa firma
   `by_istanza`, stessa derivazione via `anagrafiche.clienti`). Niente vista, niente colonna
   materializzata (il dato cambia nel tempo → si calcola in lettura).
3. **Coerenza (istanza, BA) §3 del brief: già garantita strutturalmente** dalla FK
   `fk_clienti_billing_account (billing_account_id, istanza_utility_id)` di `anagrafiche.clienti`.
   La funzione restituisce un BA che appartiene per costruzione a quell'istanza → **non**
   serve invocare `script.fn_check_utility_istanza_coerenza`.
4. **Ambito seed `azione_ui` ridimensionato (verificato sul DB)**: esistono solo i
   `tipi_prestazione` PREVENTIVI (9002/9003) e i template `template_flussi` 9001–9008.
   **Non esistono template OFFERTA/CONTRATTO** → `APRI_OFFERTA`/`APRI_CONTRATTO` non sono
   seedabili oggi. Si segue il precedente di `handler_flussi` (1 riga = 1 consumatore reale):
   si seeda **solo `APRI_PREVENTIVO`** e lo si aggancia ai 2 step `PREVENTIVAZIONE` (id 9002, 9006).
   Le voci offerta/contratto entreranno nel catalogo quando nasceranno i loro flussi.
5. **`azione_ui_params` rinviato (YAGNI)**: se servirà parametrizzazione per-template
   (mirror di `handler_params`), si aggiungerà `template_flussi.azione_ui_params jsonb NOT NULL
   DEFAULT '{}'` al 2° caso reale. Non ora.

## 2. Deliverable A — Catalogo attività UI + aggancio su template

### A1 — `00_schema/pratiche/20260615-01-create-azioni-ui-mctit.yaml`

Tabella registry, **specchio di `handler_flussi`** (stesse colonne, stessi trigger di audit;
PK `INTEGER GENERATED BY DEFAULT AS IDENTITY`, no `tx_id`/`storicizza` — come `handler_flussi`).

```sql
CREATE TABLE pratiche.azioni_ui (
    id            integer GENERATED BY DEFAULT AS IDENTITY,
    azione_ui_key varchar(100) NOT NULL,
    codice        varchar(50)  NOT NULL,
    descrizione   text         NOT NULL,
    attivo        boolean      NOT NULL DEFAULT true,
    meta          jsonb        NOT NULL DEFAULT '{}',
    data_insert   timestamptz  NOT NULL DEFAULT now(),
    user_insert   text         NOT NULL DEFAULT CURRENT_USER,
    data_update   timestamptz  NOT NULL DEFAULT now(),
    user_update   text         NOT NULL DEFAULT CURRENT_USER,
    CONSTRAINT pk_azioni_ui        PRIMARY KEY (id),
    CONSTRAINT uq_azioni_ui_key    UNIQUE (azione_ui_key),
    CONSTRAINT uq_azioni_ui_codice UNIQUE (codice)
);
COMMENT ON TABLE  pratiche.azioni_ui IS 'Catalogo attività UI lanciabili dal flusso di pratica (specchio FE di handler_flussi). La chiave azione_ui_key è risolta dal registry FE UI_ACTIVITY_REGISTRY → componente/drawer di dominio.';
COMMENT ON COLUMN pratiche.azioni_ui.azione_ui_key IS 'Token risolto lato FE (es. APRI_PREVENTIVO). Non interpretato dal DB.';
```

- **Trigger di audit**: applicare lo stesso set di `handler_flussi`
  (`script.trgfn_audit_data_user_generic` su BEFORE INS/UPD). Copiare 1:1 dalla doc auto-gen
  di `handler_flussi` per non divergere.
- `preConditions`: `not tableExists pratiche.azioni_ui` (onFail MARK_RAN).
- `rollback`: `DROP TABLE pratiche.azioni_ui`.

## 3. Deliverable B — Pratica espone il billing account derivato

### B1 — `20_code/script/20260615-03-create-fn-get-billing-account-by-istanza-mctit.yaml`

Funzione STABLE, **specchio di `fn_get_stato_cliente_by_istanza`** (stesso schema `script`,
stessa forma `by_istanza`). `runOnChange: true`, `validCheckSums: [ANY]`.

```sql
CREATE OR REPLACE FUNCTION script.fn_get_billing_account_by_istanza(p_istanza_id bigint)
 RETURNS bigint
 LANGUAGE plpgsql
 STABLE
AS $function$
BEGIN
    -- Scopo: billing account del cliente attivo per l'istanza utility.
    -- NULL se prospect (nessun cliente) → il preventivo ammette BA nullo,
    -- offerta/contratto gating lato FE (requiresActiveClient).
    -- Coerenza (istanza, BA) garantita dalla FK fk_clienti_billing_account
    -- (billing_account_id, istanza_utility_id): il BA appartiene per costruzione
    -- a questa istanza → nessun bisogno di fn_check_utility_istanza_coerenza.

    -- Guard input esplicito (read resolver: NULL/invalid → NULL, non raise,
    -- coerente con il fratello fn_get_stato_cliente_by_istanza).
    IF p_istanza_id IS NULL OR p_istanza_id <= 0 THEN
        RETURN NULL;
    END IF;

    RETURN (
        SELECT c.billing_account_id
        FROM anagrafiche.clienti c
        WHERE c.istanza_utility_id = p_istanza_id
        ORDER BY c.id DESC          -- difensivo; UNIQUE(istanza_utility_id) garantisce 1 riga
        LIMIT 1
    );
END
$function$;

COMMENT ON FUNCTION script.fn_get_billing_account_by_istanza(bigint)
IS 'Restituisce il billing_account_id del cliente attivo per l''istanza utility, NULL se prospect. Specchio di fn_get_stato_cliente_by_istanza. Coerenza (istanza,BA) garantita dalla FK clienti.';
```

> **Nota guard**: si ritorna `NULL` su input non valido invece di sollevare (deroga
> consapevole alla regola generica "ID NULL/≤0 → errore"): è un **resolver di lettura**,
> non un punto di mutazione, e il caso "istanza assente / prospect" è legittimo.
> Allineato al comportamento del fratello `fn_get_stato_cliente_by_istanza`.

**Consumo (fuori scope DB, citato per contesto)**: il BE proietta nella query dettaglio
pratica `script.fn_get_billing_account_by_istanza(p.istanza_utility_id) AS billing_account_id`
— zero logica di dominio nel BE, un solo punto di verità nel DB.
